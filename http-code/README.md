# سؤال ۱ — چگونه می‌توان یک سرویس را فقط روی شبکه داخلی اجرا کرد؟

برای محدود کردن دسترسی به یک سرویس و جلوگیری از دسترسی مستقیم کاربران اینترنت باید محل گوش‌دادن سرویس مسیریابی شبکه و قواعد Firewall به‌درستی تنظیم شوند.

### ۱. استفاده از آدرس خصوصی

در شبکه‌های IPv4 محدوده‌های خصوصی مطابق RFC 1918 عبارت‌اند از:

| محدوده | بازه |
|---|---|
| خصوصی اول | `10.0.0.0/8` |
| خصوصی دوم | `172.16.0.0/12` |
| خصوصی سوم | `192.168.0.0/16` |

این آدرس‌ها برای استفاده در شبکه‌های خصوصی در نظر گرفته شده‌اند و در اینترنت عمومی مسیریابی نمی‌شوند. بنابراین می‌توان سرویس را روی یک IP خصوصی مانند `192.168.1.10` اجرا کرد تا دسترسی به آن به مسیرهای شبکه داخلی وابسته باشد.

البته خصوصی بودن IP به‌تنهایی تضمین امنیت نیست تنظیمات مسیریابی NAT و Firewall نیز باید بررسی شوند.

### ۲. محدود کردن آدرس Bind سرویس

هر سرویس هنگام اجرا می‌تواند روی یک آدرس مشخص گوش دهد:

- `127.0.0.1`: فقط از طریق Loopback همان سیستم قابل دسترسی است.
- یک IP خصوصی مانند `192.168.1.10`: روی همان رابط شبکه داخلی گوش می‌دهد.
- `0.0.0.0`: روی تمام رابط‌های IPv4 سیستم گوش می‌دهد.

بنابراین اگر سرویس فقط باید از همان ماشین قابل دسترسی باشد Bind کردن آن به `127.0.0.1` مناسب است. اگر سایر میزبان‌های شبکه داخلی نیز باید به آن دسترسی داشته باشند می‌توان آن را روی IP داخلی Bind کرد و دسترسی را با Firewall محدود نمود.

استفاده از `0.0.0.0` به معنی عمومی شدن قطعی سرویس نیست اما باعث می‌شود سرویس روی تمام رابط‌های IPv4 گوش دهد در نتیجه قواعد شبکه و Firewall اهمیت بیشتری پیدا می‌کنند.

### ۳. اعمال محدودیت با Firewall

با Firewall می‌توان دسترسی به پورت سرویس را فقط برای مبدأهای مورد اعتماد مجاز کرد. برای مثال اگر سرویس روی پورت `8081` اجرا شود می‌توان اتصال به این پورت را فقط از Subnet داخلی سازمان پذیرفت و سایر اتصال‌ها را مسدود کرد.

در معماری این تمرین پورت Backend نباید از اینترنت یا مستقیماً از میزبان‌های غیرمجاز قابل دسترسی باشد. فقط Reverse Proxy باید امکان اتصال به Backend را داشته باشد.

### ۴. جداسازی سرویس در شبکه داخلی و استفاده از Reverse Proxy

راهکار مناسب برای مسئله تمرین این است که Reverse Proxy در نقطه ورودی قرار بگیرد و سرویس Legacy در شبکه داخلی باقی بماند:

```text
                 Internet
                    |
                    v
             Reverse Proxy
              (Port 8080)
                    |
             Private Network
                    |
                    v
              Legacy Service
               (Port 8081)
```

در این معماری درخواست‌های خارجی ابتدا به Proxy می‌رسند. Proxy پس از اعمال کنترل‌های امنیتی درخواست مجاز را به سرویس داخلی ارسال می‌کند. پورت Backend نباید مستقیماً روی اینترنت منتشر شود.

### نتیجه

برای اجرای یک سرویس فقط در شبکه داخلی باید از IP خصوصی یا رابط مناسب استفاده کرد آدرس Bind سرویس را محدود نمود قواعد Firewall را تنظیم کرد و از انتشار مستقیم پورت Backend جلوگیری کرد. در سناریوی این تمرین قرار دادن سرویس Legacy پشت Reverse Proxy و محدود کردن دسترسی شبکه‌ای به آن راهکار مناسبی است.

# سؤال ۲ — فلسفه TLS Termination چیست؟

عبارت TLS مخفف Transport Layer Security است و برای امن‌سازی ارتباطات شبکه استفاده می‌شود. HTTPS در واقع HTTP است که ارتباط آن با TLS محافظت می‌شود.

رویکرد TLS اهداف امنیتی مهمی دارد:

1. **محرمانگی (Confidentiality):** داده‌های مبادله‌شده در مسیر ارتباط رمزنگاری می‌شوند.
2. **تمامیت (Integrity):** تغییر غیرمجاز داده‌ها در مسیر ارتباط قابل شناسایی است.
3. **احراز هویت (Authentication):** معمولاً کلاینت با بررسی گواهی دیجیتال هویت سرور را بررسی می‌کند.

### ۲. TLS Termination

در معماری Reverse Proxy می‌توان ارتباط HTTPS را در خود Proxy خاتمه داد. در این حالت کلاینت با HTTPS به Proxy متصل می‌شود و Proxy پس از دریافت و رمزگشایی درخواست آن را به Backend ارسال می‌کند.

```text
Client
  |
  | HTTPS (encrypted)
  v
Reverse Proxy
  |
  | TLS Termination
  | Decryption
  |
  | HTTP (inside private network)
  v
Legacy Service
```

به بیان دیگر مسئولیت ارائه گواهی TLS و مدیریت ارتباط HTTPS از سرویس Legacy به Reverse Proxy منتقل می‌شود.

### ۳. چرا از TLS Termination استفاده می‌کنیم؟

ممکن است سرویس قدیمی امکان پشتیبانی از HTTPS یا مدیریت گواهی دیجیتال را نداشته باشد. با قرار دادن Reverse Proxy در جلوی آن می‌توان بدون تغییر کد Backend ارتباط امن HTTPS را در نقطه ورودی فراهم کرد.

مهم‌ترین مزایا عبارت‌اند از:

- مدیریت متمرکز گواهی‌های دیجیتال و تمدید آن‌ها
- کاهش پیچیدگی پیاده‌سازی TLS در سرویس‌های قدیمی
- امکان ارائه HTTPS به کلاینت‌ها بدون تغییر سرویس Legacy
- متمرکز کردن برخی سیاست‌های امنیتی در Reverse Proxy
- امکان ترکیب TLS با احراز هویت JWT و کنترل دسترسی.

### ۴. محدودیت و نکته امنیتی

روش TLS Termination به‌تنهایی ارتباط بین Proxy و Backend را رمزنگاری نمی‌کند. اگر Proxy پس از خاتمه TLS از HTTP برای ارتباط با Backend استفاده کند داده‌ها در مسیر داخلی به‌صورت رمزنگاری‌نشده منتقل می‌شوند.

این روش فقط زمانی قابل قبول است که شبکه داخلی مورد اعتماد و به‌اندازه کافی محافظت شده باشد. اگر شبکه داخلی نیز در معرض شنود یا دست‌کاری است باید از TLS مجدد (Re-encryption) یا Mutual TLS (mTLS) بین Proxy و Backend استفاده کرد.

همچنین TLS و JWT دو وظیفه متفاوت دارند:

| TLS | JWT |
|---|---|
| از ارتباط در مسیر محافظت می‌کند. | اطلاعات هویتی و Claims توکن را در اختیار سامانه قرار می‌دهد. |
| محرمانگی و تمامیت ارتباط را فراهم می‌کند. | امکان اعتبارسنجی توکن و اعمال کنترل دسترسی را فراهم می‌کند. |
| به‌تنهایی مجاز بودن کاربر برای استفاده از یک API را تعیین نمی‌کند. | به‌تنهایی ارتباط شبکه را رمزنگاری نمی‌کند. |


در TLS Termination Reverse Proxy نقطه پایان ارتباط TLS با کلاینت است و مدیریت HTTPS و گواهی دیجیتال را بر عهده می‌گیرد. این روش برای محافظت از سرویس‌های Legacy مفید است اما امنیت مسیر Proxy تا Backend باید جداگانه بررسی شود.

## تولید توکن آزمایشی

اسکریپت `scripts/generate_token.py` فقط برای ساخت توکن آزمایشی و محلی است و از کتابخانه‌های استاندارد Python استفاده می‌کند.

```
python scripts/generate_token.py
```
## آزمایش درخواست‌ها

### ۱. درخواست بدون توکن

curl.exe -i http://localhost:8080/get

نتیجه :

```text
HTTP/1.1 401 Unauthorized
```

### ۲. درخواست با توکن معتبر

```
curl.exe -i -H "Authorization: Bearer $TOKEN" http://localhost:8080/get
```

نتیجه مورد انتظار: پاسخ موفق از سرویس `go-httpbin` معمولاً با وضعیت `200 OK`.

### ۳. درخواست با توکن جعلی

```
curl.exe -i -H "Authorization: Bearer invalid-token" http://localhost:8080/get
```

نتیجه:

```text
HTTP/1.1 401 Unauthorized
```

### ۴. بررسی Endpoint مربوط به Headerها

```
curl.exe -i -H "Authorization: Bearer $TOKEN" http://localhost:8080/headers
```

Proxy هدر Authorization را پس از اعتبارسنجی حذف می‌کند تا توکن احراز هویت به سرویس Legacy منتقل نشود.
