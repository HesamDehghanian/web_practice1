## سؤال ۱: تفاوت نسخه‌های HTTP و دلیل استفاده از UDP در HTTP/3

### تفاوت نسخه‌ها

-   نسخه **HTTP/0.9:** 
نسخه‌ای بسیار ساده فقط از درخواست `GET` پشتیبانی
    می‌کرد سربرگ و کد وضعیت نداشت و پاسخ عملاً محتوای سند بود.
-   نسخه **HTTP/1.0:** نسخه و کد وضعیت را به پیام‌ها اضافه کرد. سربرگ‌ها
    روش‌هایی مانند `POST` و `HEAD` و امکان ارسال انواع مختلف محتوا با
    `Content-Type` نیز فراهم شدند. در حالت معمول برای هر درخواست اتصال
    جداگانه‌ای ایجاد و پس از پاسخ بسته می‌شد.
-   نسخه **HTTP/1.1:** اتصال‌های پایدار را به‌صورت پیش‌فرض پشتیبانی کرد
    بنابراین چند درخواست می‌توانند از یک اتصال TCP استفاده کنند. سربرگ
    `Host` انتقال قطعه‌ای (`chunked transfer encoding`) کنترل بهتر کش و
    مذاکره بر سر نوع محتوا نیز از قابلیت‌های مهم آن هستند.
-   نسخه **HTTP/2:** قالب پیام‌ها را به فریم‌های دودویی تبدیل کرد و امکان ارسال
    هم‌زمان چند جریان (multiplexing) روی یک اتصال TCP را فراهم کرد.
    فشرده‌سازی سربرگ‌ها با HPACK نیز سربار ارتباط را کاهش می‌دهد. با این
    حال از آنجا که همچنان بر TCP متکی است ازدست‌رفتن یک بسته می‌تواند بر
    تحویل داده‌های جریان‌های مختلف همان اتصال اثر بگذارد.
-   نسخه **HTTP/3:** همان معنا و روش‌های اصلی HTTP را با استفاده از پروتکل
    انتقال QUIC ارائه می‌کند. QUIC روی UDP ساخته شده و قابلیت‌هایی مانند
    انتقال قابل‌اعتماد جریان‌های مستقل و رمزنگاری مبتنی بر TLS 1.3 را
    فراهم می‌کند.

### چرا HTTP/3 از UDP استفاده می‌کند؟

چون کهUDP به‌خودی‌خود تضمین تحویل ترتیب یا ارسال مجدد داده‌ها را ارائه نمی‌دهد
اما QUIC این قابلیت‌های لازم را در لایه‌ای بالاتر پیاده‌سازی می‌کند. در
HTTP/2 ازدست‌رفتن بسته‌های TCP ممکن است تحویل داده‌های تمام جریان‌های روی
همان اتصال را متوقف کند. در QUIC جریان‌ها تا حد زیادی مستقل‌اند و اختلال
در یک جریان لزوماً جریان‌های دیگر را متوقف نمی‌کند. همچنین برقراری اتصال و
مذاکره رمزنگاری می‌تواند با رفت‌وبرگشت‌های شبکه‌ای کمتری انجام شود و در
شرایط مناسب تغییر شبکه نیز آسان‌تر مدیریت شود. بنابراین دلیل اصلی انتخاب
UDP استفاده از QUIC برای کاهش تأخیر و بهبود عملکرد است نه اینکه UDP
به‌تنهایی قابل‌اعتمادتر از TCP باشد.


## سؤال ۲: ارتباط‌های Stateless و Stateful


### الف) توضیح دسته‌بندی

در ارتباط **stateless** سرور برای رسیدگی به هر درخواست به سابقهٔ
درخواست‌های قبلی همان کاربر وابسته نیست درخواست باید اطلاعات لازم برای
پردازش خود را همراه داشته باشد. در ارتباط **stateful** سرور وضعیت یا
سابقهٔ تعامل را نگه می‌دارد و درخواست‌های بعدی می‌توانند به آن وضعیت وابسته
باشند. برای مثال یک درخواست مستقل برای دریافت یک صفحه می‌تواند stateless
باشد درحالی‌که یک نشست ورود کاربر که وضعیت آن در سرور ذخیره می‌شود
رفتاری stateful ایجاد می‌کند.

### ب) HTTP در کدام دسته قرار می‌گیرد و چگونه مشکل مدیریت وضعیت حل می‌شود؟

پروتکل HTTP از نظر معنای اصلی پروتکل stateless است یعنی خود پروتکل الزام
نمی‌کند که سرور وضعیت درخواست‌های قبلی را برای پردازش درخواست فعلی نگه
دارد. با این حال برنامه‌های وب می‌توانند با استفاده از سازوکارهایی مانند
Cookie شناسهٔ نشست (session ID) نشست ذخیره‌شده در سرور و توکن‌هایی
مانند JWT وضعیت کاربردی را مدیریت کنند. برای نمونه سرور می‌تواند پس از
ورود موفق شناسهٔ نشست را در یک Cookie قرار دهد و مرورگر آن را در
درخواست‌های بعدی ارسال کند. در این حالت HTTP همچنان stateless است اما
برنامه روی آن وضعیت کاربر را مدیریت می‌کند.


## سؤال ۳: محدودیت مدل Client/Server و راهکارهای آن


### الف) توضیح چالش

در مدل معمول HTTP کلاینت درخواست را آغاز می‌کند و سرور در پاسخ به همان
درخواست داده می‌فرستد. بنابراین سرور معمولاً نمی‌تواند بدون وجود یک درخواست
یا کانال ارتباطی برقرار پیامی را مستقیماً به کلاینتی که پشت NAT یا
فایروال قرار دارد ارسال کند. این محدودیت برای اعلان‌های فوری پیام‌رسانی
رویدادهای webhook و سامانه‌های هشداردهی مشکل ایجاد می‌کند زیرا برنامه
ممکن است بخواهد به‌محض وقوع رویداد اطلاعاتی را به سمت مصرف‌کننده بفرستد.

### ب) راهکارهای متداول

**راهکار Polling (پرس‌وجوی دوره‌ای):** کلاینت در بازه‌های زمانی مشخص درخواست
می‌فرستد و می‌پرسد آیا داده یا رویداد جدیدی وجود دارد یا خیر. این روش ساده
است و به زیرساخت ویژه‌ای نیاز ندارد اما درخواست‌های تکراری می‌توانند
ترافیک و بار سرور را افزایش دهند و فاصلهٔ بین دو پرس‌وجو باعث تأخیر در
دریافت رویداد شود. این روش برای مواردی مناسب است که تأخیر کم اهمیت حیاتی
ندارد.

**راهکار Long Polling (پرس‌وجوی طولانی):** کلاینت درخواست می‌فرستد اما سرور
تا زمان آماده‌شدن رویداد یا رسیدن به مهلت زمانی پاسخ را باز نگه می‌دارد.
پس از دریافت پاسخ کلاینت بلافاصله درخواست دیگری ایجاد می‌کند. این روش در
مقایسه با polling معمولی می‌تواند تعداد درخواست‌های بی‌نتیجه را کم کند و
بدون نیاز به اتصال دائمی اختصاصی کار کند بااین‌حال مدیریت مهلت زمانی
قطع اتصال و مقیاس‌پذیری آن پیچیده‌تر است.

**راهکار Server-Sent Events (SSE):** کلاینت یک اتصال HTTP برقرار می‌کند و
سرور رویدادها را در همان پاسخ به‌صورت جریانی ارسال می‌کند. این روش برای
اعلان‌ها و به‌روزرسانی‌های یک‌طرفه از سرور به کلاینت مناسب است و مرورگرها از
طریق `EventSource` از آن پشتیبانی می‌کنند. SSE برای ارتباط دوطرفه طراحی
نشده است کلاینت برای ارسال داده همچنان می‌تواند درخواست HTTP جداگانه
بفرستد.

**راهکار WebSocket:** کلاینت اتصال را آغاز می‌کند و پس از برقراری اتصال
WebSocket دو طرف می‌توانند از طریق همان اتصال پیام ارسال کنند. این روش
برای چت بازی‌های آنلاین و تعاملات بلادرنگ دوطرفه مناسب است. در مقابل به
پشتیبانی WebSocket در سرور و زیرساخت شبکه نیاز دارد و مدیریت اتصال‌های
طولانی احراز هویت و مقیاس‌پذیری باید در نظر گرفته شود.

**راهکار Webhook (درخواست برگشتی به یک endpoint):** اگر سامانهٔ تولیدکنندهٔ
رویداد بتواند به یک نشانی عمومی از سامانهٔ دریافت‌کننده دسترسی داشته باشد
هنگام رخ‌دادن رویداد یک درخواست HTTP معمولاً از نوع `POST` به آن نشانی
می‌فرستد. این روش در اتصال سرویس‌های مستقل مانند اطلاع‌دادن نتیجهٔ پرداخت
یا تغییر وضعیت یک کار رایج است. دریافت‌کننده باید endpoint قابل‌دسترسی
داشته باشد و امضای پیام یا روش مناسب دیگری برای اعتبارسنجی جلوگیری از
پردازش تکراری و مدیریت تلاش مجدد را پیاده‌سازی کند. Webhook محدودیت آغاز
ارتباط را حذف نمی‌کند بلکه سامانهٔ تولیدکننده در این حالت خودش کلاینت
HTTP است و به endpoint دریافت‌کننده درخواست می‌فرستد.

## سؤال ۴: مشخص‌کردن اجزای URL


``` text
ss://asghar:1234!!@ss.myproxy.com:1234#shadowSocks1
```
در URL داده‌شده، بخش **Scheme** برابر با `ss` است که نوع URI را مشخص می‌کند و در این مثال برای Shadowsocks به کار رفته است. بخش **User Information** شامل مقدار `asghar:1234!!` است که پیش از علامت `@` قرار دارد؛ با فرض قالب متداول `username:password`، نام کاربری `asghar` و رمز عبور `1234!!` است.

بخش **Host** برابر با `ss.myproxy.com` است و نام میزبان مقصد را مشخص می‌کند. بخش **Port** نیز مقدار `1234` را دارد و شمارهٔ درگاهی را نشان می‌دهد که برای اتصال استفاده می‌شود.

در این URL، بخش **Path** وجود ندارد؛ زیرا پس از میزبان و شمارهٔ درگاه، مسیر مشخصی ارائه نشده است. همچنین، بخش **Query** نیز وجود ندارد، چون هیچ پارامتری پس از علامت `?` قرار نگرفته است.

در نهایت، بخش **Fragment** برابر با `shadowSocks1` است که پس از علامت `#` قرار دارد و معمولاً به‌عنوان شناسه یا برچسبی برای تفسیر محلی استفاده می‌شود. این بخش در درخواست HTTP به سرور ارسال نمی‌شود.

نکته: تفسیر دقیق بخش اطلاعات کاربری به قالب اختصاصی برنامه‌ای بستگی دارد
که این URI را مصرف می‌کند. در ساختار عمومی URI کل رشتهٔ `asghar:1234!!`
بخش user information محسوب می‌شود.


## سؤال ۵: انتخاب HTTP Status Code مناسب برای هر سناریو


### ۱. پایگاه دادهٔ وب‌سایت دچار مشکل شده و درخواست‌های ورود انجام نمی‌شوند.

-   کد **`500 Internal Server Error`**: اگر خطای پیش‌بینی‌نشده‌ای در برنامه یا
    هنگام ارتباط با پایگاه داده رخ داده باشد و سرور نتواند درخواست را
    تکمیل کند.
-   کد **`503 Service Unavailable`**: اگر سرویس موقتاً به دلیل تعمیرات یا
    اضافه‌بار در دسترس نباشد.
-   کد **`504 Gateway Timeout`**: اگر یک gateway یا reverse proxy برای
    دریافت پاسخ از سرویس بالادستی مانند سرویس احراز هویت یا پایگاه داده
    از طریق یک سرویس واسط بیش از مهلت مجاز منتظر بماند.

انتخاب دقیق به علت واقعی خطا بستگی دارد. صرفاً خراب‌بودن پایگاه داده
به‌تنهایی به معنی `504` نیست.

### ۲. نام کاربری واردشده در سایت وجود ندارد و ورود موفق نیست.

-   کد **`401 Unauthorized`**: اگر درخواست به احراز هویت نیاز دارد و
    اطلاعات معتبر احراز هویت ارائه نشده یا اعتبار آن‌ها تأیید نشده است.
-   کد **`404 Not Found`**: در صورتی که API عمداً برای کاربر ناشناخته پاسخ
    یکسانی با منبع ناموجود بدهد تا وجود یا عدم وجود حساب را افشا نکند
    این انتخاب به طراحی API بستگی دارد.

برای یک endpoint ورود `401` معمولاً انتخاب قابل‌انتظاری است پیام پاسخ
بهتر است اطلاعات غیرضروری دربارهٔ وجود حساب افشا نکند.

### ۳. وب‌سایت به دامنهٔ دیگری منتقل شده است.

-   کد **`301 Moved Permanently`**: وقتی انتقال دائمی است و کلاینت باید از
    URL جدید استفاده کند.
-   کد **`308 Permanent Redirect`**: وقتی انتقال دائمی است و لازم است روش
    درخواست و بدنهٔ آن حفظ شود.
-   اگر انتقال فقط موقت باشد **`302 Found`** یا
    کد **`307 Temporary Redirect`** مناسب‌تر است `307` روش درخواست را حفظ
    می‌کند.

برای انتقال دائمی یک وب‌سایت `301` انتخاب رایجی است.

### ۴. تعداد درخواست‌های کاربر از نرخ مجاز بیشتر شده است.

-   کد **`429 Too Many Requests`**: کد مشخص برای محدودیت نرخ درخواست (rate
    limiting). در صورت امکان سرور می‌تواند سربرگ `Retry-After` را نیز
    برای اعلام زمان مناسب تلاش مجدد ارسال کند.

### ۵. تمدید JWT موفق بوده و توکن جدید در سربرگ بازگردانده شده است.

-   کد **`200 OK`**: اگر عملیات تمدید موفق شده و پاسخ توکن جدید را در
    سربرگ یا بدنه بازمی‌گرداند.
-   کد **`204 No Content`**: اگر عملیات موفق بوده اما سرور عمداً هیچ محتوایی
    در بدنهٔ پاسخ نمی‌فرستد. استفاده از این کد تنها زمانی مناسب است که
    قرارداد API با آن سازگار باشد.

در سناریوی گفته‌شده چون توکن جدید در سربرگ پاسخ برگردانده می‌شود
`200 OK` انتخاب روشن و مناسبی است.

### ۶. کاربر از یک بازهٔ IP ممنوعه برای دسترسی به سرویس استفاده می‌کند.

-   کد **`403 Forbidden`**: اگر سرور درخواست را فهمیده اما به دلیل سیاست
    دسترسی از جمله مسدودبودن IP اجازهٔ انجام آن را نمی‌دهد.
-   کد **`401 Unauthorized`** برای این سناریو مناسب نیست مگر اینکه مشکل
    اصلی مربوط به احراز هویت باشد ممنوعیت IP به‌خودی‌خود مسئلهٔ احراز هویت
    نیست.


## سؤال ۶: تشخیص نوع پروکسی در هر سناریو

### ۱. استفاده از سرورهای داخلی دانشگاه به‌جای سرورهای مرکزی برای دریافت بسته‌ها از package manager مانند apt

**نوع: Forward Proxy / Caching Proxy (پروکسی رو به جلو یا پروکسی
کش‌کننده)**

در این حالت کلاینت‌های داخل دانشگاه درخواست دریافت بسته را به سرور واسط
یا mirror داخلی می‌فرستند. اگر سرور داخلی نقش کش یا آینهٔ مخزن را داشته
باشد بسته‌ها را از منبع بالادستی دریافت یا از نسخهٔ ذخیره‌شده ارائه می‌کند
و در درخواست‌های بعدی ترافیک خارجی و زمان دریافت کاهش می‌یابد. از نظر
دقیق معماری یک mirror مخزن لزوماً HTTP forward proxy نیست اما در چارچوب
دسته‌بندی آموزشی پروکسی‌ها این سناریو به نقش پروکسی رو به جلو/کش‌کننده
نزدیک است.

### ۲. تقسیم درخواست‌ها بر اساس مبدأ جغرافیایی درخواست‌ها

**نوع: Reverse Proxy همراه با Geo-routing یا Global Load Balancing**

یک reverse proxy یا لایهٔ توزیع بار می‌تواند با توجه به کشور منطقه یا محل
تقریبی درخواست آن را به سرور مناسب هدایت کند. این کار ممکن است برای
کاهش تأخیر رعایت الزامات منطقه‌ای یا توزیع بار بین مراکز داده انجام شود.
در سامانه‌های بزرگ این تصمیم ممکن است در لایهٔ DNS شبکهٔ توزیع محتوا
(CDN) یا یک سرویس global load balancing گرفته شود بنابراین پیاده‌سازی
دقیق الزاماً فقط یک reverse proxy منفرد نیست.

### ۳. اضافه‌کردن قابلیت احراز هویت به یک سرویس بسیار قدیمی

**نوع: Reverse Proxy با قابلیت احراز هویت (Authentication Gateway)**

می‌توان یک reverse proxy را جلوی سرویس قدیمی قرار داد تا پیش از عبور دادن
درخواست به سرویس اصلی هویت کاربر و مجوز دسترسی او را بررسی کند. در این
معماری سرویس قدیمی پشت پروکسی باقی می‌ماند و لازم نیست حتماً برای
پشتیبانی از روش احراز هویت جدید تغییر داده شود. پروکسی پس از تأیید هویت
درخواست مجاز را به سرویس ارسال می‌کند و درخواست نامعتبر را رد می‌کند.
طراحی باید به انتقال امن اطلاعات هویتی اعتماد سرویس پشت پروکسی به
سربرگ‌ها و جلوگیری از دسترسی مستقیم و دورزدن پروکسی توجه کند.
