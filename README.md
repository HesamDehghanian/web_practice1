## سؤال ۱: تفاوت `merge` و `rebase`

هر دو دستور برای ترکیب تغییرات شاخه‌ها (branchها) استفاده می‌شوند اما تاریخچهٔ کامیت‌ها را به شکل متفاوتی نگه می‌دارند.

### `git merge`

دستور `merge` تغییرات یک شاخه را با شاخه فعلی ترکیب می‌کند. اگر دو شاخه از هم جدا شده باشند معمولا یک merge commit با دو والد ساخته می‌شود. کامیت‌های قبلی تغییر نمی‌کنند و شناسه آن‌ها ثابت می‌ماند بنابراین تاریخچه نشان می‌دهد که توسعه در چند شاخه به‌صورت موازی پیش رفته است.

```bash
git switch main
git merge feature
```

**چه زمانی مناسب است؟** برای نمونه وقتی قابلیت جدیدی در شاخه `feature` تکمیل شده و می‌خواهیم آن را وارد `main` کنیم می‌توانیم از `merge` استفاده کنیم. این روش تاریخچهٔ قبلی را بازنویسی نمی‌کند و ادغام شاخه را نیز در تاریخچه مشخص نگه می‌دارد. اگر شاخه مقصد از قبل نوک شاخه دیگر را در خود داشته باشد ممکن است Git به‌جای ساختن merge commit فقط شاخه را جلو ببرد (fast-forward)

### `git rebase`

دستور `rebase` کامیت‌های شاخه فعلی را بر پایه نوک شاخه دیگری دوباره اعمال می‌کند. چون والد کامیت‌ها عوض می‌شود کامیت‌های بازسازی‌شده شناسه‌های جدیدی می‌گیرند. در نتیجه تاریخچه معمولا خطی‌تر می‌شود و در حالت معمول merge commit جدیدی ساخته نمی‌شود.

```bash
git switch feature
git rebase main
```

**چه زمانی مناسب است؟** فرض کنید روی شاخه شخصی `feature` کار می‌کنم و در این فاصله `main` جلو رفته است. می‌توانم پیش از ادغام شاخه خودم را روی آخرین نسخه `main` باز پایه‌گذاری کنم تا تغییراتم بر اساس نسخه جدیدتر باشد و تاریخچه مرتب‌تر بماند.

**تفاوت اصلی:** `merge` تاریخچهٔ شاخه‌ها را حفظ می‌کند `rebase` کامیت‌ها را دوباره می‌سازد و تاریخچه را بازنویسی می‌کند. به همین دلیل بهتر است کامیت‌هایی را که روی شاخه مشترک منتشر شده‌اند و دیگران بر اساس آن‌ها کار می‌کنند بدون هماهنگی `rebase` نکنیم.

## سؤال ۲: انتخاب بخشی از تغییرات

در خروجی `git diff` یک hunk بخشی از تغییرات است که به‌صورت یک بلوک نمایش داده می‌شود. هر hunk معمولا با خطی مانند `@@ -10,6 +10,8 @@` شروع می‌شود این خط محل تغییر را در نسخه قبلی و نسخه جدید فایل نشان می‌دهد. چند خط اطراف تغییر نیز ممکن است برای درک بهتر زمینه نمایش داده شوند.

برای دیدن تغییرات به‌صورت تعاملی و انتخاب بخش‌هایی که باید وارد staging شوند از این دستور استفاده می‌کنم:

```bash
git add -p app.py
```

گیت هر hunk را جداگانه نشان می‌دهد و دربارهٔ آن تصمیم می‌گیرد. گزینه‌های مهم عبارت‌اند از:

- گزینه `y`: این hunk وارد staging شود.
- گزینه `n`: این hunk وارد staging نشود.
- گزینه `s`: تلاش برای شکستن hunk به بخش‌های کوچک‌تر.
- گزینه `e`: ویرایش دستی patch برای انتخاب دقیق‌تر خطوطی که stage می‌شوند.
- گزینه `q`: خروج از حالت تعاملی.
- گزینه `?`: نمایش راهنما.

پس از انتخاب بخش‌ها با دستور زیر بررسی می‌کنم که دقیقا چه چیزی آماده کامیت است:

```bash
git diff --staged
```

سپس اگر محتوا درست بود آن را کامیت می‌کنم:

```bash
git commit -m "Describe the change"
```

بخش‌هایی که stage نشده‌اند در working tree باقی می‌مانند و می‌توان آن‌ها را در کامیت دیگری ثبت کرد.

**فایدهٔ این روش** این است که می‌توانم تغییرات نامرتبط یک فایل را در کامیت‌های جداگانه قرار دهم برای مثال اصلاح یک باگ را از تغییر ظاهری یا تغییر نام جدا کنم. در این صورت هر کامیت هدف روشن‌تری دارد بازبینی آن آسان‌تر است و در صورت نیاز می‌توان اثر یک تغییر مشخص را راحت‌تر برگرداند.

## سؤال ۳: یافتن منشأ خطا با `git bisect`

دستور `git bisect` با استفاده از جست‌وجوی دودویی کامیتی را پیدا می‌کند که احتمالاً خطا را وارد کرده است. برای شروع باید یک کامیت سالم و یک کامیت معیوب داشته باشیم. Git سپس کامیتی از میانهٔ بازه را انتخاب می‌کند با مشخص‌کردن سالم یا معیوب بودن آن محدودهٔ جست‌وجو هر بار تقریباً نصف می‌شود.

برای مثال اگر کامیت فعلی معیوب باشد و نسخه `v1.0` سالم بوده باشد مراحل شروع به این صورت است:

```bash
git bisect start
git bisect bad
git bisect good v1.0
```

سپس Git یک کامیت میانی را checkout می‌کند. برنامه یا تست مربوط را اجرا می‌کنم و نتیجه را اعلام می‌کنم:

```bash
git bisect good   # اگر این نسخه سالم است
git bisect bad    # اگر این نسخه هم خطا دارد
```

این روند را تا مشخص‌شدن اولین کامیت معیوب ادامه می‌دهم. در پایان Git شناسهٔ کامیتی را که خطا را وارد کرده گزارش می‌کند. برای پایان جست‌وجو و بازگشت به شاخه یا وضعیت قبلی نیز می‌توانم اجرا کنم:

```bash
git bisect reset
```

اگر تست قابل اجرا به‌صورت خودکار باشد می‌توان از دستور زیر هم استفاده کرد:

```bash
git bisect run ./test.sh
```

در این حالت کد خروجی صفر به معنی موفقیت تست و کد خروجی غیرصفر به معنی شکست آن است بنابراین اسکریپت باید این قرارداد را درست رعایت کند.

**مثال:** فرض کنید برنامه در نسخه `v1.0` درست کار می‌کرده اما اکنون خروجی یک تابع اشتباه است و بین این دو وضعیت 64 کامیت وجود دارد. بررسی تک‌تک کامیت‌ها زمان‌بر است اما جست‌وجوی دودویی در حالت ایده‌آل حدود 6 مرحله لازم دارد چون 

این روش به‌جای بررسی حدسی همه تغییرات محدوده جست‌وجو را مرحله‌به‌مرحله کوچک می‌کند و معمولا پیدا کردن منشا خطا را سریع‌تر می‌سازد.

## سؤال ۴: بررسی تغییرات پیش از کامیت

### ۱. بررسی وضعیت مخزن و تغییرات

برای بررسی وضعیت کلی مخزن از این دستور استفاده می‌کنم:

```bash
git status
```

این دستور نشان می‌دهد کدام تغییرات وارد staging شده‌اند کدام تغییرات هنوز stage نشده‌اند و چه فایل‌هایی untracked هستند. برای دیدن جزئیات تغییرات نیز از این دو دستور استفاده می‌کنم:

```bash
git diff
git diff --staged
```

- دستور `git diff` تغییرات working tree را نسبت به staging نشان می‌دهد یعنی تغییراتی که هنوز stage نشده‌اند.
- دستور `git diff --staged` تغییرات staging را نسبت به آخرین کامیت (`HEAD`) نشان می‌دهد یعنی محتوایی که در صورت اجرای کامیت بعدی ثبت خواهد شد. `git diff --cached` نیز معادل آن است.

در سناریوی سؤال ابتدا بخشی از تغییرات `README.md` را stage کرده‌ام و بعد دوباره همان فایل را ویرایش کرده‌ام. بنابراین ممکن است `README.md` در هر دو بخش `Changes to be committed` و `Changes not staged for commit` در خروجی `git status` دیده شود.

### ۲. کامیت بدون گزینهٔ `-a`

اگر دستور معمولی `git commit` را بدون `-a` اجرا کنم فقط محتوای موجود در staging وارد کامیت می‌شود:

- تغییراتی که قبلا stage کرده‌ام با همان وضعیت ذخیره‌شده در staging وارد کامیت می‌شوند.
- ویرایش‌های بعدی که دوباره stage نشده‌اند در کامیت قرار نمی‌گیرند و به‌صورت تغییرات unstaged در working tree باقی می‌مانند.

دلیلش این است که Git کامیت را از snapshot ناحیه staging می‌سازد نه مستقیماً از آخرین وضعیت فایل‌های working tree. گزینه `-a` فایل‌های tracked تغییرکرده را پیش از کامیت stage می‌کند اما در صورت سؤال این گزینه استفاده نمی‌شود.

### ۳. نادیده‌گرفتن پوشهٔ `tmp/`

برای اینکه فایل‌های موقت و untracked داخل پوشهٔ `tmp/` در آینده به‌طور تصادفی وارد کامیت نشوند در فایل `gitignore` واقع در ریشهٔ مخزن این الگو را می‌نویسم:

```gitignore
/tmp/
```

اسلش ابتدایی مشخص می‌کند که الگو مربوط به پوشهٔ `tmp` در ریشهٔ مخزن است. برای تنظیمی که فقط در مخزن محلی خودم اعمال شود و با دیگران به اشتراک گذاشته نشود می‌توانم به‌جای آن از `.git/info/exclude` استفاده کنم.

آیا `gitignore` برای فایلی که قبلا tracked شده کافی است؟ خیر. این فایل به‌تنهایی ردیابی فایل‌هایی را که قبلا tracked شده‌اند متوقف نمی‌کند. اگر بخواهم فایلی را از ردیابی خارج کنم اما نسخه آن روی دیسک باقی بماند از این دستور استفاده می‌کنم:

```bash
git rm --cached path/to/file
```

برای پوشه در صورت نیاز می‌توان از `git rm -r --cached path/to/directory` استفاده کرد. پس از آن باید تغییر مربوط به حذف از ردیابی را کامیت کنم. البته اگر هدف فقط نادیده‌گرفتن فایل‌های موقت جدید داخل `tmp/` باشد و آن فایل‌ها tracked نباشند همان الگوی `.gitignore` کافی است.

## سؤال ۵: رفع `merge conflict` در کار گروهی

### ۱. چرا conflict رخ داده است؟

در این سناریو هر دو شاخه از یک کامیت مشترک شروع شده‌اند و یک خط از `README.md` را به دو متن متفاوت تغییر داده‌اند. Git نمی‌تواند با اطمینان تشخیص دهد کدام متن باید در نسخه نهایی باقی بماند به همین دلیل هنگام merge تعارض گزارش می‌کند.

البته هر تغییری که دو نفر در یک فایل انجام دهند الزاماً conflict ایجاد نمی‌کند. اگر تغییرها در بخش‌های جدا از هم باشند Git معمولا می‌تواند آن‌ها را خودکار ترکیب کند. تعارض معمولا زمانی رخ می‌دهد که تغییرهای متفاوت روی یک بخش هم‌پوشانی داشته باشند.

### ۲. شناسایی فایل‌های متعارض و نسخه‌ها

برای دیدن وضعیت merge و فایل‌های حل‌نشده از این دستورها استفاده می‌کنم:

```bash
git status
git diff --name-only --diff-filter=U
```

داخل فایل متعارض Git معمولا دو نسخه را با **conflict marker** مشخص می‌کند. برای نمونه

- بخش `<<<<<<< HEAD` شروع متن شاخه فعلی را نشان می‌دهد.
- بخش `=======` دو نسخه را از هم جدا می‌کند.
- بخش `>>>>>>> feature-description` پایان متن شاخه در حال ادغام را مشخص می‌کند.

نامی که پس از `>>>>>>>` می‌آید معمولا نام شاخه در حال ادغام است. در این تمرین نام شاخه قابلیت `feature-description` است.

### ۳. مراحل حل conflict و تکمیل merge

چون فرض سؤال این است که باید اطلاعات هر دو تغییر حفظ شود ابتدا فایل را باز می‌کنم و متن نهایی مناسبی می‌نویسم که محتوای لازم از هر دو نسخه را در خود داشته باشد. سپس همهٔ conflict markerها را حذف می‌کنم. مراحل کلی به این صورت است:

```bash
git switch main
git merge feature-description
git status
```

پس از اینکه تعارض گزارش شد فایل `README.md` را ویرایش می‌کنم و نسخه نهایی را نگه می‌دارم. بعد فایل حل‌شده را stage می‌کنم و merge را کامل می‌کنم:

```bash
git add README.md
git diff --staged
git merge --continue
```

اگر Git به‌جای `git merge --continue` از روند معمول کامیت برای تکمیل ادغام استفاده کند می‌توان از `git commit` نیز استفاده کرد. پیش از تکمیل merge تغییرات stage‌شده را بازبینی می‌کنم تا مطمئن شوم متن نهایی همان چیزی است که می‌خواهم.

برای بررسی اینکه markerها در فایل باقی نمانده‌اند می‌توانم اجرا کنم:

```bash
grep -nE '^(<<<<<<<|=======|>>>>>>>)' README.md
git status
```

اگر دستور `grep` هیچ خروجی ندهد markerهایی با این الگو در فایل پیدا نشده‌اند. در `git status` نیز نباید فایل حل‌نشده‌ای باقی مانده باشد. سپس مطمئن می‌شوم که متن نهایی از نظر محتوایی درست است حذف markerها به‌تنهایی تضمین نمی‌کند که ادغام منطقی درست انجام شده باشد.

### ۴. لغو merge

اگر هنگام بررسی متوجه شوم که فعلاً نباید merge انجام شود می‌توانم عملیات در حال انجام را با دستور زیر لغو کنم:

```bash
git merge --abort
```

این دستور تلاش می‌کند مخزن را به وضعیت پیش از شروع merge برگرداند. طبق صورت سؤال working tree پیش از merge تمیز بوده است بنابراین لغو merge باید وضعیت پیشین را بازگرداند.

## سؤال ۶: انتخاب روش مناسب برای بازگرداندن تغییرات

### ۱. کنار گذاشتن تغییرات unstaged در `notes.txt`

در این حالت تغییرات فایل وارد staging نشده‌اند و می‌خواهم فقط تغییرات همین فایل را دور بریزم. دستور مناسب این است:

```bash
git restore notes.txt
```

این دستور محتوای working tree فایل را با نسخه staging جایگزین می‌کند. طبق صورت سؤال نسخه staging با آخرین کامیت یکسان است بنابراین تغییرات انجام‌شده در `notes.txt` کنار گذاشته می‌شوند. staging تاریخچه و فایل‌های دیگر تغییر نمی‌کنند.

 این کار تغییرات ثبت‌نشدهٔ فایل را دور می‌ریزد پیش از اجرای آن باید مطمئن شوم که به آن تغییرات نیاز ندارم.

### ۲. خارج‌کردن `notes.txt` از staging و حفظ ویرایش‌ها

اگر فایل را اشتباهی stage کرده باشم اما بخواهم ویرایش‌ها در working tree باقی بمانند از این دستور استفاده می‌کنم:

```bash
git restore --staged notes.txt
```

این دستور نسخه staging فایل را به وضعیت `HEAD` برمی‌گرداند اما محتوای working tree را تغییر نمی‌دهد. در نتیجه فایل از فهرست تغییرات آمادهٔ کامیت خارج می‌شود و ویرایش‌ها به‌صورت unstaged باقی می‌مانند. تاریخچهٔ کامیت‌ها نیز تغییری نمی‌کند.

### ۳. خنثی‌کردن یک کامیت اشتباه که روی `main` push شده است

در این سناریو کامیت اشتباه روی شاخه مشترک `main` منتشر شده و هم‌تیمی‌ها هم آن را دریافت کرده‌اند. چون هدف خنثی‌کردن اثر کامیت بدون حذف یا بازنویسی تاریخچه است از `git revert` استفاده می‌کنم:

```bash
git revert <hash-of-bad-commit>
git push origin main
```

به‌جای `<hash-of-bad-commit>` شناسهٔ کامیت اشتباه را قرار می‌دهم. دستور `git revert` یک کامیت جدید می‌سازد که تغییرات کامیت موردنظر را معکوس می‌کند خود کامیت اشتباه در تاریخچه باقی می‌ماند. چون طبق صورت سؤال کامیت موردنظر یک کامیت معمولی است نه merge commit نیازی به گزینهٔ `-m` نیست.

 حذف کامیت از تاریخچه یا `push --force` مناسب نیست چون

- کامیت روی شاخه مشترک منتشر شده و دیگران آن را دریافت کرده‌اند بازنویسی تاریخچه می‌تواند مخزن محلی آن‌ها را با مخزن راه دور ناسازگار کند.
- دستور `push --force` ممکن است کامیت‌های جدیدی را که دیگران در همین فاصله push کرده‌اند از شاخه راه دور کنار بزند.
- استفاده از `revert` تاریخچه را حفظ می‌کند اثر تغییر اشتباه را با یک کامیت جدید خنثی می‌کند و برای شاخه مشترک معمولا انتخاب امن‌تری است.
